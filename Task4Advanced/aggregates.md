## Bounded Context: Пациентский контекст
### Агрегат: Patient (PatientAgg)
Границы агрегата: вся информация о пациенте, необходимая для идентификации и взаимодействия.

#### Ключи
- patient_id (UUID) — первичный ключ, глобально уникальный идентификатор пациента.

#### Инварианты
- Обязательность заполнения ФИО и даты рождения при регистрации.
- Валидность СНИЛС (формат и уникальность).
- Согласованность контактных данных (телефон, email).
- Соответствие статусов пациента (активен/заблокирован/архив) бизнес‑правилам.
- Наличие явного согласия пациента на обработку персональных данных.

#### Операции
- register() — создание записи пациента с валидацией обязательных полей.
- update_contact() — обновление контактных данных с проверкой формата.
- give_consent() — фиксация согласия на обработку данных.

## Bounded Context: Медицинский контекст
### Агрегат: EpisodeOfCare (EpisodeAgg)

#### Границы агрегата
данные об эпизоде лечения, включая диагнозы и статус.

#### Ключи
- episode_id (UUID) — первичный ключ эпизода.
- patient_id (UUID) — внешний ключ на агрегат Patient.

#### Инварианты
- Дата окончания эпизода не может быть раньше даты начала.
- Эпизод должен иметь хотя бы один диагноз при закрытии.
- Статус эпизода должен соответствовать его жизненному циклу (открыт → закрыт).
- При закрытии эпизода обязательно указывается исход лечения.

#### Операции
- start_episode() — инициализация нового эпизода с проверкой прав доступа врача.
- close_episode() — закрытие эпизода с фиксацией исхода.
- add_diagnosis() — добавление диагноза с проверкой медицинской терминологии.

## Bounded Context: Кредитный контекст
### Агрегат: CreditApplication (CreditAppAgg)

#### Границы агрегата
заявка на кредит, включая скоринговые данные.

#### Ключи
- application_id (UUID) — первичный ключ заявки.
- customer_id (UUID) — ссылка на пациента (через ACL).

#### Инварианты
- Сумма кредита должна быть положительной.
- Срок кредита в пределах допустимого диапазона (3–60 мес.).
- Риск‑оценка должна быть рассчитана до утверждения.
- Заявка может быть одобрена только один раз.

#### Операции
- submit() — подача заявки с проверкой базовых критериев.
- approve() — утверждение с фиксацией ставки.
- reject() — отклонение с указанием причины.

### Агрегат: CreditAgreement (CreditAgreementAgg)

#### Границы агрегата
подписанный кредитный договор.

#### Ключи
- agreement_id (UUID) — первичный ключ договора.
- application_id (UUID) — связь с заявкой.

#### Инварианты
- Договор создаётся только для одобренной заявки.
- Расчет ежемесечного платежа
- Ставка по договору не может превышать одобренную.

#### Операции
- sign() — подписание договора клиентом.
- activate() — активация договора после зачисления средств.

## 4. Bounded Context: Платёжный контекст
### Агрегат: Transaction (TransactionAgg)

#### Границы агрегата
платёжная операция и её статус.

#### Ключи
- transaction_id (UUID) — уникальный идентификатор транзакции.

#### Инварианты
- Сумма транзакции положительная.
- Счёт отправителя и получателя не совпадают.
- Транзакция может быть отменена только в статусе «ожидает подтверждения».
- После выполнения транзакция не редактируется.

#### Операции
- execute() — проведение платежа с проверкой баланса.
- rollback() — отмена транзакции с восстановлением средств.

## 5. Bounded Context: Медицинский анализ
### Агрегат: AnalysisRequest (AnalysisAgg)
#### Границы агрегата
запрос на анализ медицинских данных и его результаты.

#### Ключи
- request_id (UUID) — идентификатор запроса.
- patient_id (UUID) — ссылка на пациента.

#### Инварианты
- Тип анализа должен быть из утверждённого перечня.
- Уровень уверенности (confidence_score) в диапазоне 0–1.
- Результаты анализа не могут быть изменены после завершения.

#### Операции
- start_analysis() — запуск анализа с проверкой наличия данных.
- complete_analysis() — фиксация результатов с оценкой качества.

## 6. Bounded Context: Аналитика и витрины
### Агрегат: DataMart (DataMart)

#### Границы агрегата
агрегированные данные для отчётности.

#### Ключи 
- mart_name (String) — тип витрины (patient_mart, finance_mart и т. д.).

#### Инварианты
- Данные обновляются только через потоковую обработку.
- Целостность данных проверяется при каждом обновлении.
- Витрины содержат обезличенную информацию.

#### Операции
- refresh() — обновление данных с контролем времени выполнения.
- query() — выполнение запросов с ограничением по объёму.

## 7. Bounded Context: Персонал
### Агрегат: StaffMember (StaffAgg)

#### Границы агрегата
данные сотрудника клиники.

#### Ключи
- staff_id (UUID) — уникальный идентификатор сотрудника.

#### Инварианты
- Должность должна быть из штатного расписания.
- Сотрудник может быть привязан только к одному отделу.
- Уволенный сотрудник не может выполнять операции.

#### Операции
- hire() — приём на работу с проверкой квалификации.
- update_role() — изменение должности с согласованием.
- terminate() — увольнение с архивированием данных.

## 8. Bounded Context: Инвентаризация
### Агрегат: InventoryItem (InventoryAgg)
#### Границы агрегата
единица учёта запасов.
#### Ключи
- item_id (UUID) — идентификатор позиции.
- sku (String) — артикул производителя.

#### Инварианты
- Текущий остаток не может быть отрицательным.
- Уровень повторного заказа положительный.
- Порог оповещения настраивается по категориям.

#### Операции
- update_stock() — изменение остатка с логированием.
- check_threshold() — проверка уровня запасов.

## 9. Bounded Context: Безопасность
### Агрегат: User (UserAgg)
#### Границы агрегата
учётная запись пользователя системы.

#### Ключи
- user_id (UUID) — идентификатор пользователя.
- email (String) — уникальный адрес для входа.
#### Инварианты
- Email валиден и уникален.
- Роль назначается из утверждённого списка.
- Аккаунт блокируется после 5 неудачных попыток входа.

#### Операции
- authenticate() — проверка пароля и MFA.
- assign_role() — назначение роли с аудитом.
- enable_mfa() — активация двухфакторной аутентификации.

## 10. Антикоррупционный слой (ACL)
### Агрегаты: ClinicACL, FintechACL
#### Границы:
трансформации данных между легаси‑системами и доменными моделями.

#### Ключи
 отсутствуют (служебные агрегаты).

#### Инварианты

- Сохранение семантики данных при преобразовании.
- Обезличивание медицинских данных перед публикацией.
- Логирование всех преобразований.

#### Операции
- Трансляция форматов (Legacy → Domain).
- Фильтрация полей по политикам безопасности.
- Общие принципы для всех агрегатов
- Границы агрегатов соответствуют бизнес‑сущностям и их жизненным циклам.
- Инварианты проверяются при выполнении операций.
- Ключи обеспечивают уникальность и связи между агрегатами.
- События публикуются только после успешного завершения операции и валидации инвариантов.
- Изменения состояния фиксируются атомарно внутри агрегата.
