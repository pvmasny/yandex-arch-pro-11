# AS-IS
- Все данные и логика в одном месте --> Сложность масштабирования, высокая стоимость изменений
- Долгое формирование сложных отчетов --> Негативно сказывается на пользовательском опыте
- Монолит --> Долгий time to market
- Legacy технологии	SQL Server 2008, PowerBuilder --> Риски безапасности, сложность найма

# To-Be
## Преимущества событийного подхода

### Гибкость
- Микросервисная архитектура
  - Каждый домен развивтается независимо
- Простота интеграции (подписка в новых сервисах)

### Масштабируемость
- Горизонтальное масштабирование
- Каждый микросервис масштабируется исходя из своих метрик
- Параллельная обработка за счет партицирования (Kafka)

### Скорость обработки
- Асинхронная обработка -- нет ожидания от других сервисов
- Разные подписчики обрабатывают события одновременно
- Частые запросы кешируются (Redis)

### Надежность и отказоусточивость
- Гарантии доставки (Kafka гарантирует доставку)
- Применение паттернов Outbox гарантирют отправку сообщений в Kafka
- Необработанные события сохраняются для анализа

## Вывод

Переход на событийную архитектуру для «Будущее 2.0» обеспечивает:
- Гибкость — независимое развитие доменов, быстрое подключение новых партнёров
- Масштабируемость — горизонтальное масштабирование каждого компонента
- Скорость — real-time отчётность, высокую пропускную способность
- Надёжность — отсутствие единой точки отказа, гарантии доставки
- Соответствие требованиям — изоляция медицинских данных, аудируемость
- В отличие от текущей архитектуры с централизованным DWH и ESB, событийный подход позволяет:
- Сократить time-to-market в 6-12 раз
- Увеличить производительность аналитики в разы
- Упростит расширение/интеграции системы в будущем
